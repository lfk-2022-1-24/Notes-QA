# 多轮追问（指代消解 + 跑题）问题总结与修复

## 1. 问题现象

系统当前是单轮 RAG 问答（每次只处理一个问题），因此会出现两类追问问题：

### A) 指代不理解（缺少对话记忆）

示例：

1. 用户先问：**“垂直拆分的优点是什么？”**
2. 用户再问：**“它的缺点是什么？”**

如果系统不携带历史上下文，第二问中的“它”无法解析，检索会漂移到不相关内容或直接返回找不到。

### B) 追问后回答跑题（命中了包含多主题的大段落）

在某些笔记（例如包含“垂直拆分/水平拆分/分库分表/问题”等多个主题的长段落）中，即使第二问被正确改写为“垂直拆分的缺点是什么？”，LLM 仍可能：

- 先答“垂直拆分缺点”
- 再顺带扩展“水平拆分缺点 / 分库分表带来的问题”

造成“看起来回答错了主题”的体验。

---

## 2. 根因分析

### A) 指代问题根因

- 默认实现是无状态的：每次 `POST /api/ask` 只拿到当前 `question`
- “它/他的/其/上一个/上述”等代词需要依赖上一轮问题或答案来确定指代对象

### B) 跑题根因

RAG 检索返回的 chunk 可能同时包含多个主题：

- 既包含“垂直拆分的缺点”
- 也包含“水平拆分的缺点”
- 甚至包含“分库分表带来的问题/分布式事务/跨节点 join”

当 LLM 看到这些内容，即使问题是“垂直拆分的缺点”，也容易顺带把后续主题一起总结出来。

---

## 3. 修复方案（已落地）

### 3.1 传递对话历史（前端）

在前端 `ChatPanel` 中维护最近几轮 `{question, answer}`，每次请求 `/api/ask` 时携带：

- `history: [{ question, answer }, ...]`（最多保留最近 6 轮）

文件：`src/components/ChatPanel.tsx`

### 3.2 查询改写（后端检索前的指代消解）

在后端 `POST /api/ask` 中：

1. 接收 `history`
2. 调用 `rewriteStandaloneQuestion(question, history)` 将追问改写为独立问句

例如：

- “它的缺点是什么？” → “垂直拆分的缺点是什么？”

文件：`src/lib/llm.ts`（新增 `rewriteStandaloneQuestion`）

### 3.3 主题聚焦（避免跑题）

在后端从改写后的问题中提取聚焦信息：

- `topic`：例如“垂直拆分”
- `aspect`：例如“优点/缺点”

并做两层约束：

1. **候选排序加权**：优先包含 `topic`（以及 `优点/缺点`）的 chunk
2. **喂给 LLM 的 sources 做裁剪**：只截取包含 topic/aspect 附近的片段，避免 LLM 看到后续无关主题
3. **LLM 提示聚焦**：在 user message 中附加 Focus 指令（只回答该 topic，不扩展其他主题）

文件：

- `src/app/api/ask/route.ts`（`extractFocus` / `clipToFocusedSection` / 聚焦筛选）
- `src/lib/llm.ts`（`AskOptions` + Focus 指令）

---

## 4. 如何验证修复是否生效

### 4.1 指代消解验证

上传包含“垂直拆分优缺点”的笔记后，连续提问：

1. “垂直拆分的优点是什么？”
2. “它的缺点是什么？”

检查第二问返回中 `rewrittenQuestion` 是否为：

- “垂直拆分的缺点是什么？”

### 4.2 跑题控制验证

检查第二问答案是否**只讨论垂直拆分缺点**，不再扩展到：

- 水平拆分缺点
- 分库分表带来的问题

---

## 5. 可选优化（下一步）

- **Questions-only history**：默认只传最近 N 轮问题（更省 token）；当检测到“第2点/上面第3条”这类强依赖答案内容时，再升级为带 answer。
- **QA-aware 分块**：对 Markdown 的 `Q\d+`、标题、小节做结构化分块，让“主题 + 结论”更集中，减少跑题。
- **Rerank**：对 TopN 候选用更强的模型重排序，进一步提高 precision、降低噪声 sources。
