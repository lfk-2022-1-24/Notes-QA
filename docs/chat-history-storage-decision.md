# 聊天历史存储：浏览器 vs 数据库（决策记录）

## 背景

目前系统是单用户、无登录的 Notes QA（RAG）应用。用户希望能够**回看历史提问与回答**，并在刷新页面后不丢失。

---

## 当前实现选择

**将聊天历史保存到浏览器 `localStorage`**（最多保留最近 50 条消息），并提供 `Clear` 按钮清空。

相关实现：`src/components/ChatPanel.tsx`

---

## 为什么不默认存数据库

在当前产品形态下（无账号/无多用户），把聊天历史写入数据库会引入额外复杂度与风险：

- **缺少用户/会话身份**：没有登录体系时，必须先定义“这条记录属于谁”（cookie clientId、匿名用户、设备标识等）。
- **实现与运维成本更高**：需要新增表结构、迁移、API、读写与清理策略，且会增加 DB 压力。
- **隐私风险更高**：聊天内容可能包含敏感信息（问题、摘要、推理结论），默认落库会扩大数据暴露面与合规要求。
- **不影响核心价值链路**：应用核心是“笔记入库 + 检索 + 引用回答”，聊天记录持久化不应成为主链路阻塞点。

因此默认选择：**本地优先**，先满足“可回看、刷新不丢”。

---

## 浏览器存储的优缺点

### 优点
- **零后端依赖**：无需新增 API / 表结构 / 迁移
- **成本低**：无额外 token/DB 开销
- **隐私更友好**：数据保存在用户本机
- **响应更快**：读写本地，体验更顺滑

### 缺点
- **无法跨设备同步**：换浏览器/换电脑会丢
- **清理不可控**：用户清浏览器数据会丢
- **无法做服务端审计/回放**：不适合需要留存的业务

---

## 什么时候应该升级为数据库存储

满足任意一项，建议落库：

- **跨设备同步**（手机/电脑共享同一会话）
- **多用户隔离**（登录后每个用户的独立历史）
- **合规/审计/回放**（需要服务端留存）
- **运营分析/质量评估**（需要统计或追踪）
- **更强的长期记忆**（跨会话 user profile、偏好、长期任务）

---

## 推荐的“最小可用”数据库方案（无登录也可用）

如果仍不做登录，也可以用“匿名 clientId”实现隔离：

- **浏览器生成 `clientId`**：存 cookie（或 localStorage）并随请求发送
- **后端按 `clientId` 落库**：实现同一设备的持久化与查询

建议表结构（最小两表）：
- `conversations`：`id`, `client_id`, `created_at`, `title?`
- `messages`：`id`, `conversation_id`, `role`, `content`, `sources_json`, `created_at`

并保留前端 localStorage 作为缓存（离线/性能），数据库作为长期存储与跨端能力的基础。

---

## 结论

在当前“单用户 + 无登录”的阶段，**浏览器 localStorage 是更合理的默认实现**；当产品目标扩展到跨设备/多用户/审计分析时，再升级为数据库存储。
